Your first agent task in 5 minutes

Beginner · 5 min · No prior agent experience needed

The fastest way to understand Sunday is to give it a small, real task and watch what happens. You'll go from install to a reviewed, merged diff in about five minutes.

  1. Open a scratch folder

    Create an empty folder anywhere and open it in Sunday (File → Open Folder). A scratch folder is ideal — there's nothing to break.

  2. Open the agent panel

    Click the Sunday Agent icon in the activity bar (left sidebar). If this is your first run, sign in with GitHub, Google, or Microsoft when prompted — this activates your 200 req/day free tier.

  3. Describe a concrete task

    Type something specific and verifiable, for example:

    Create a Python script called organizer.py that moves every .txt file
in this folder into a subfolder named by today's date (YYYY-MM-DD),
skips files already organized, and prints a summary. Add a short
README.md explaining how to run it.

    Specific beats vague: name the files, the behavior, and the edge cases you care about.

  4. Watch the plan

    Before writing code, the agent shows its plan: the steps it intends to take and the files it will touch. Read it. If something looks wrong, edit your prompt and re-run — steering early is ten times cheaper than fixing later.

  5. Review the diff, then accept

    When the agent finishes, you get a diff — not a blob of pasted code. Review each change, run the script yourself (python organizer.py), then accept. Congratulations: you've done agent-driven development.

What you just learned: the core loop — prompt → plan → execute → review. Every advanced workflow in Sunday is this loop, scaled up.

Chaining parallel agents

Intermediate · 15 min · Requires: first-task tutorial

One agent is a helper. Multiple agents on one task is a team. This tutorial shows how to decompose a realistic feature so parallel agents actually help instead of colliding.

  1. Pick a decomposable task

    Good candidates have independent parts. Example: "Add a settings page with three sections (Profile, Notifications, Billing), each with its own form, validation, and tests." Bad candidates: "Fix this one-line bug" — decomposition overhead isn't worth it.

  2. Prompt with explicit boundaries

    Tell the orchestrator how to split the work:

    Build the settings page as three parallel tracks:
1. Profile section (form + validation + tests)
2. Notifications section (form + validation + tests)
3. Billing section (form + validation + tests)
Shared: use the existing Card and Input components, follow the
patterns in src/pages/account.jsx. Run all tests at the end.
  3. Inspect the task tree

    Sunday shows the decomposition before executing: three worker nodes plus a verifier. Check that the file scopes don't overlap unexpectedly — if two nodes claim the same file, say so and let the planner re-scope.

  4. Let them run, watch Mission Control

    Open Mission Control to see all three agents live. You'll notice the pool limit in action: on a 2-agent plan, the third node queues until a worker frees up. This is intentional — bounded parallelism protects your machine.

  5. Review the verifier's report

    The verifier runs the full test suite and checks each node's acceptance criteria. If a node fails, it goes back for rework automatically — you only see the final, verified diff.

Rule of thumb: parallelize across files and modules, not within a single function. If two agents would edit the same 50 lines, keep it sequential.

Setting up scheduled tasks

Intermediate · 10 min · Requires: a project with tests

Scheduled tasks are cron for agents: plain-language recurring jobs that run via the sundayd daemon, even when the IDE is closed.

  1. Open the scheduler

    In the Sunday Agent panel, go to the Scheduled tab and click New task.

  2. Describe the job in plain language

    Example: "Every weekday at 8am, run the test suite in this project. If anything fails, summarize which tests failed and what changed recently that might have caused it. Save the report to reports/daily-health.md." Be as specific as you were in the first-task tutorial — the agent that runs at 8am only has your description to work with.

  3. Pick a schedule

    Use a preset (daily, weekdays, weekly) or a cron expression. Start with something frequent while testing — you can relax it later. For the first run, use Run once now to validate the task works before it goes on autopilot.

  4. Choose the delivery

    Decide where results go: a desktop notification, a file in the workspace, or both. For reports you'll actually read, file + notification is the sweet spot.

  5. Check the run history

    After a few runs, open the task's history. You'll see each execution, its output, and any errors. If a run fails, the error is shown with the agent's log — fix the description and re-run.

Ideas for scheduled tasks: nightly dependency-outdated checks, Monday-morning changelog drafts from the week's commits, daily "what's broken on main" summaries for team leads.

Using Second Brain effectively

Intermediate · 10 min · Requires: a few days of Sunday usage

Second Brain is Sunday's persistent memory. Used well, it's the difference between briefing a new contractor every morning and working with someone who knows your project. Used poorly, it's a junk drawer. Here's how to keep it sharp.

  1. Seed it deliberately

    Open the Second Brain panel and add your project's durable facts up front: "We use pnpm, not npm", "API base URL comes from VITE_API_URL", "All utils need unit tests", "Prefer composition over inheritance in React components." Five minutes of seeding saves hours of repeated corrections.

  2. Let it learn, then curate

    As you work, Sunday extracts new facts automatically. Once a week, skim the recent additions: keep what's durable, delete what's stale (that "temporary workaround" from March is not a convention). Memory quality compounds — in both directions.

  3. Scope memories to projects

    Facts can be global or project-scoped. Keep project conventions (framework choices, API patterns) scoped to the project; keep personal preferences (editor style, communication tone) global. This prevents your React conventions from leaking into your Python project.

  4. Reference it in prompts

    You can invoke memory explicitly: "Refactor this following our testing conventions" pulls the relevant Second Brain facts into the agent's context with higher priority. Useful when the automatic recall misses something.

  5. Audit before sharing

    If you enable cloud sync or export a project, review what's in memory first. Second Brain can accumulate API endpoints, internal hostnames, and other things you may not want leaving the machine. The panel shows everything; delete freely.

The test: after two weeks, prompt "set up a new module like the others" and see if the agent matches your conventions without being told. If it does, your Second Brain is working.

Best-of-N for tricky refactors

Advanced · 20 min · Requires: comfort with parallel agents

For high-stakes changes — architecture decisions, tricky refactors, API design — the first solution is rarely the best. Best-of-N runs N agents with deliberately different strategies, then lets you compare.

  1. Choose a decision worth the compute

    Best-of-N costs N times the requests. Reserve it for choices you'll live with: "Refactor the data-fetching layer — it's tangled across 12 files and every new feature touches it." Not for renaming a variable.

  2. Enable Best-of-N and set N=3

    In the agent panel, toggle Best-of-N and set the candidate count. Three is the sweet spot: enough diversity to matter, cheap enough to run casually. Five for truly consequential decisions.

  3. Give strategy hints, not solutions

    Prompt the goal and let the strategies vary naturally — or nudge them: "Explore different approaches: one minimal-change, one clean-slate redesign, one incremental migration path." The value is in the diversity of approaches.

  4. Compare in the diff view

    When candidates are ready, the comparison view shows them side by side: diffs, test results, and each agent's written rationale. Read the rationales — they often surface trade-offs you hadn't considered, which is half the value.

  5. Pick, merge, or steal

    You don't have to take one winner wholesale. Common outcome: pick candidate B's structure with candidate A's migration strategy. Tell the agent what to combine and it produces the final merged change for review.

Pro move: save the losing candidates' rationales in your project docs. Six months later, "why did we choose this approach" will be answered — with the alternatives you already evaluated.
